Why Ingress?

You already know Pods run your app, Deployments scale it, and Services expose it inside the cluster. Ingress answers the next question: how do outside users reach many services through one entry point?

Kubernetes building blocks
Building blockWhat it does
PodRuns your app container
DeploymentKeeps N pods running; handles scaling and rollouts
ServiceStable internal address for a set of pods (Layer 4)
IngressRoutes outside HTTP/HTTPS traffic to Services by domain or path (Layer 7)

Problems it solves

Route by domain or URL path · terminate HTTPS in one place · put many services behind one public IP (one load balancer = lower cost).

Simple mental model

Ingress is the receptionist at the front door of your cluster: it reads the address on each request and sends it to the right room (Service).

Ingress vs Ingress Controller

The most common confusion: an Ingress object does nothing on its own.

Ingress resource vs controller
Ingress (resource)Ingress Controller
RoleThe rulebookThe traffic cop
What it iskind: Ingress YAMLA Deployment running NGINX / Traefik / HAProxy
Where it livesStored in the Kubernetes APIRuns as pods behind a LoadBalancer Service

How a request flows

  1. User opens example.com.
  2. DNS resolves it to the load balancer IP.
  3. The load balancer forwards the request to the Ingress Controller.
  4. The controller matches the host and path rules and picks a Service.
  5. The Service forwards the request to one of its Pods.

Pattern 1 — Host-based routing

Different domains go to different services, all sharing one IP. Use it when each product or team has its own sub-domain.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: host-based-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app-service
                port:
                  number: 80
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80

Pattern 2 — Path-based routing

Same domain, different URL paths go to different services.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: path-based-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: example.com
      http:
        paths:
          - path: /app
            pathType: Prefix
            backend:
              service:
                name: app-service
                port:
                  number: 80
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
pathType options
pathTypeDoes /api match…Notes
Prefix/api, /api/, /api/usersMost common
ExactOnly /apiStrict match
ImplementationSpecificDepends on the controllerNeeded for regex paths in NGINX

Longest matching path wins: /api/v2 beats /api beats /.

Host + path combined

One Ingress can mix both styles: some rules match a domain plus a path, others just a domain.

spec:
  ingressClassName: nginx
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /cart
            pathType: Prefix
            backend: { service: { name: cart-service, port: { number: 80 } } }
          - path: /orders
            pathType: Prefix
            backend: { service: { name: orders-service, port: { number: 80 } } }
    - host: blog.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: blog-service, port: { number: 80 } } }
    - host: docs.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: docs-service, port: { number: 80 } } }

Enabling HTTPS with TLS

The controller holds the certificate and decrypts traffic; inside the cluster traffic usually continues as plain HTTP.

Step 1 — Create the TLS secret

kubectl create secret tls my-tls-secret \
  --cert=cert.crt \
  --key=key.key

Step 2 — Reference it in the Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: secure-ingress
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - example.com
      secretName: my-tls-secret
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app-service
                port:
                  number: 80

Production tip

Use cert-manager with Let's Encrypt to issue and auto-renew certificates instead of creating secrets by hand.

Install the NGINX Ingress Controller

Ingress rules need a controller running in the cluster. NGINX is the most common choice.

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx --create-namespace

# Public IP / hostname to point your DNS at
kubectl get svc -n ingress-nginx ingress-nginx-controller

Full production example (microservices)

example.com → frontend, example.com/api → backend, all over HTTPS with rate limiting.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: prod-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/limit-rps: "10"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [example.com]
      secretName: example-com-tls
  rules:
    - host: example.com
      http:
        paths:
          - path: /api          # more specific first
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80

Advanced features (NGINX annotations)

Pick a tab.

Changes the URL before it reaches the backend — e.g. strip the /api prefix.

metadata:
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
    - host: example.com
      http:
        paths:
          - path: /api(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: api-service
                port:
                  number: 80

Gotcha

A plain rewrite-target: / sends every request to /. Use capture groups (above) to keep the rest of the path.

Caps requests per second per client IP to protect backends from spikes.

nginx.ingress.kubernetes.io/limit-rps: "10"

Basic auth — username/password stored in a Secret:

nginx.ingress.kubernetes.io/auth-type: basic
nginx.ingress.kubernetes.io/auth-secret: basic-auth
nginx.ingress.kubernetes.io/auth-realm: "Authentication Required"

OAuth / SSO — delegate login to an external auth service such as oauth2-proxy:

nginx.ingress.kubernetes.io/auth-url: "https://auth.example.com/oauth2/auth"
nginx.ingress.kubernetes.io/auth-signin: "https://auth.example.com/oauth2/start"

Send a small share of traffic to a new version, then raise it as confidence grows. Create a second Ingress for the same host and path, marked as canary.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
spec:
  ingressClassName: nginx
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app-v2
                port:
                  number: 80

SSL/TLS terminationNoYes
Domain-based routingNoYes

CostHigher (many LBs)Lower (one LB)

Production checklist

  • Set ingressClassName explicitly, especially with multiple controllers.
  • Automate TLS with cert-manager; force HTTPS with ssl-redirect.
  • Run 2+ controller replicas with a PodDisruptionBudget.
  • Add rate limits and auth on sensitive paths.
  • Order paths from most to least specific (/api/v2, /api, /).
  • Scrape controller metrics with Prometheus and keep access logs.
  • For new platforms, also evaluate Gateway API, the successor to Ingress.
