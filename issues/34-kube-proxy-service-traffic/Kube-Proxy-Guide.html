1Pod Networking — Every Pod Can Reach Every Pod

One of the first things we learn about Kubernetes networking: every Pod should be able to communicate with every other Pod — even across nodes. The Pod network provides an internal virtual network spanning the whole cluster.

For example: a web app on Node 1 needs to reach a database on Node 2. It can — using the database Pod's IP directly.

The web app reaches the database directly at 10.32.0.15 — the Pod network handles the cross-node hop.

2But Pod IP Addresses Are Not Permanent

A Pod is not a permanent server. Recreate it — and the new pod can get a different IP. If the web app hard-coded 10.32.0.15, it breaks the moment the database pod is recreated:

⚠ Pod IPs are not permanent — every recreate can mean a new address. This is why Services exist.

3Using a Service Instead of the Pod IP

Instead of pointing the web app at the pod's IP, we create a Service for the database. The app just connects to the name db — the Service provides a stable IP and DNS name that survives every pod recreate.

The app knows only db — the Service IP never changes even when the pod behind it does.

4Direct Pod IP vs Service — Side by Side

Same recreate scenario: direct IP breaks; the Service shields the app completely.

5So Where Does the Service Actually Run?

A Service has an IP — 10.96.0.50, say. So does the Service join the pod network? Run as a container? No — and this is the important concept.

A Service is not a pod, not a container, not a process listening on an interface. It's a virtual component — an API object that exists only inside the Kubernetes system. Nothing "sits" on 10.96.0.50.

So if no process is listening on the Service IP… how does traffic sent there reach a backend pod? That's where kube-proxy comes in.

6What Is kube-proxy?

kube-proxy is a process that runs on every node. Its job: watch for Services (and their endpoints) via the API server, then configure the node's networking so traffic sent to a Service IP reaches the right backend pods — typically by programming iptables or IPVS rules.

When a Service is created, Kubernetes knows its IP and its backend pods — kube-proxy on each node wires up the forwarding rules.

9Installing kube-proxy — Two Paths

Manual (bare binary)

VERSION="v1.36.5"
curl -LO https://dl.k8s.io/${VERSION}/bin/linux/amd64/kube-proxy
chmod +x kube-proxy && sudo mv kube-proxy /usr/local/bin/
sudo useradd --system --no-create-home --shell /usr/sbin/nologin kube-proxy
sudo mkdir -p /var/lib/kube-proxy /etc/kubernetes
# write config.yaml + proxy.conf kubeconfig, then:
sudo systemctl daemon-reload
sudo systemctl enable --now kube-proxy
sudo journalctl -u kube-proxy -f   # watch it work

11OpenShift Note — OVN-Kubernetes Replaces kube-proxy

On OpenShift 4.x with OVN-Kubernetes (the default CNI, and what lab.ocp.local runs), there is no classic kube-proxy. Service routing is programmed by OVN: the ovnkube-node DaemonSet installs OVS/OpenFlow rules on each node that do the same job — Service IP → endpoint NAT. Same mental model, different plumbing. On a OpenShiftSDN cluster, sdn pods play the kube-proxy-equivalent role.

12The Takeaway

The Pod network gives every pod reachability. Services give apps a stable IP and DNS name immune to pod recreates. And kube-proxy — invisible, on every node — is the plumbing that rewrites Service traffic onto real backend pods. Service = the address; kube-proxy = the routing.

Try it: oc get svc → pick a ClusterIP → oc get endpointslices for its backends → on a node, inspect the NAT rules (iptables -t nat -L KUBE-SERVICES upstream, or OVN flows on OCP). Watching a packet get DNAT'd from Service IP to pod IP makes this click instantly.
