1When Every Pod Looks Fine, but the Cluster Starts Struggling

Documented · reference guide

Imagine a cluster shared by three teams — dev, qa, and data. Every pod looks reasonable on its own. Then one afternoon, the data team launches a batch job that spins up dozens of pods. Nothing is "wrong" with any single pod — but together they eat the whole node pool, and dev + qa start timing out. Left: no quotas. Right: each namespace capped by its own budget.

Same three teams, same burst. Without quotas the batch job drains the shared pool; with quotas it stops at its own wall — additional pods are simply blocked.

2ResourceQuota = A Budget Per Namespace

A ResourceQuota gives each namespace a hard ceiling — like a department budget. Requests are counted against it the moment a pod is created, not while it runs. Hit the ceiling and the API server simply says no: the new pod is blocked at admission, inside the offending namespace, while every other team keeps running.

Quota counts requests (and limits) — the pod's reservation, not real usage. A pod requesting 1 CPU counts 1 CPU even while idling at 10m.

3The Governance Stack — Four Layers

ResourceQuota never works alone. Think of it as four layers, each answering one question:

Top-down: a team pool spans many projects → a wall per namespace → defaults per pod → the numbers actually counted.
The critical interaction: once a compute quota (requests.cpu / requests.memory) exists, every new pod must declare those values or admission rejects it. The LimitRange is what injects defaults so developer pods don't fail en-masse.

ClusterResourceQuotaMany namespaces (label selector)OCP-only. A team-level pool spanning dev/test/qa projects

LimitRange vs ResourceQuota — a simple way to remember the difference

LimitRange manages settings for each individual container or pod; ResourceQuota controls the combined usage of the whole namespace — the shared budget.

LimitRange cares about each pod's bounds; ResourceQuota cares about the sum of everything in the namespace.

4Where the Rejection Happens

Quota is checked by the API-server admission controller — before the object is ever stored. Not by the scheduler, not by the kubelet. Rejection is instant and atomic: the pod never exists, even partially.

Fail-fast at admission: the failure is a 403 error at create time — never a Pending pod waiting for capacity.
  • Failures surface as 403 Forbidden … exceeded quota — not Pending pods.
  • status.used is a cache refreshed asynchronously (resource-quota-sync-period, default ~5 min) — freshly deleted pods can still count briefly.
  • The object is never partially created — admission is atomic.

5What You Can Cap — Two Buckets

Quotas split into two families: compute/storage (protects the nodes) and object counts (protects the API server and etcd).

Left: the workloads' footprint. Right: etcd/API-server protection — object sprawl is a real outage source.

6OpenShift Specifics — ClusterResourceQuota

Regular ResourceQuota is per-namespace. OCP adds ClusterResourceQuota (CRQ): one shared pool across many projects, selected by label — perfect for "team A gets 12 CPU across dev, test and qa."

Selection is by namespace label (spec.selector.labels) or the openshift.io/quota annotation. Usage syncs slowly by design — plan buffer.
  • A namespace may be selected by only one CRQ.
  • Never put user quotas on openshift-*, kube-*, default.
  • The Project Request Template can inject quota + limitrange into every new project — the clean way to make quotas default-on.
  • Inspect with oc describe clusterquota <name>.

7Reference Manifests

Standard compute + object quota

apiVersion: v1
kind: ResourceQuota
metadata:
  name: app-quota
  namespace: <target-namespace>
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
    persistentvolumeclaims: "5"
    requests.storage: 50Gi
    services.loadbalancers: "0"   # no LBs here
    services.nodeports: "0"

The LimitRange that makes quotas usable

apiVersion: v1
kind: LimitRange
metadata:
  name: app-limits
  namespace: <target-namespace>
spec:
  limits:
  - type: Container
    default:        { cpu: 500m, memory: 512Mi }   # injected when pod omits limits
    defaultRequest: { cpu: 100m, memory: 128Mi }   # injected when pod omits requests
    max:            { cpu: "2",  memory: 2Gi }
    min:            { cpu: 50m,  memory: 64Mi }
With a compute quota present, undeclared requests = instant rejection. LimitRange defaults turn Pod A into Pod B automatically.

8Troubleshooting — exceeded quota

First command is always oc describe quota -n <ns> — it prints hard vs used per resource. Then walk the tree:

Read hard vs used — the resource that equals its cap is your culprit. If none do: missing requests, or quota-cache lag.

Quick diagnosis commands

# which quotas exist + usage
oc get quota -n <target-namespace>
oc describe quota <quota-name> -n <target-namespace>

# pods with NO requests (rejected once compute quota exists)
oc get pods -n <target-namespace> -o json | \
  jq -r '.items[] | select([.spec.containers[].resources.requests.cpu] | any(. == null)) | .metadata.name'

# multi-project quota
oc describe clusterquota <crq-name>

9Deploy Quotas via GitOps

Quotas are governance — they belong in Git, reviewed like any policy, not applied by hand from a ticket.

Same Application → same commit → no drift between the wall and its defaults.
Never apply a compute quota to a live namespace before its LimitRange exists. Running pods are unaffected — but every new rollout fails until pods carry requests.
