1When Every Pod Looks Fine, but the Cluster Starts Struggling

Documented · reference guide

Imagine you're managing a Kubernetes cluster shared by three teams: development, QA, and data engineering. Everything looks fine at first — each team deploys its applications, sets CPU and memory limits, and follows the usual guidelines.

Then, one afternoon, the data team starts a batch job. The job creates dozens of Pods. Every Pod has reasonable resource settings, so nothing looks wrong at the individual level. But together, those Pods consume a significant share of the cluster's resources. The dev team's new Pods sit waiting; QA's workloads take longer to start.

The problem isn't any one Pod — it's that nobody set a limit on how much the entire data namespace could consume.

Same three teams, same burst. Without quotas the batch job drains the shared pool; with quotas it stops at its own wall.

2The Budget Idea

Instead of looking at resource consumption one Pod at a time, ResourceQuota lets you define a budget for the whole namespace. Once that budget is reached, Kubernetes prevents additional resource usage that would exceed the configured quota.

Think of it as giving every team its own resource allowance, rather than letting everyone draw from the shared pool without a defined limit.

Quota counts requests (and limits) — the pod's reservation, not real usage. A pod requesting 1 CPU counts 1 CPU even while idling at 10m.

3First, Understand the Difference: LimitRange vs ResourceQuota

The two sound similar, but solve different problems. A LimitRange controls the resources assigned to individual containers or supported resource types. A ResourceQuota controls the total amount of selected resources or objects within a namespace.

Imagine a family sharing a monthly mobile data plan. Each member has an individual allowance — that's LimitRange. The family also has a total plan allowance — that's ResourceQuota.

everyone stops, no matter how small each person's share was.
The two work together: LimitRange keeps individuals sensible; ResourceQuota protects the shared pool.

Side by side

LimitRange cares about each pod's bounds; ResourceQuota cares about the sum of everything in the namespace.

4Create Your First ResourceQuota

Suppose your development team uses a namespace called dev. You want a defined CPU and memory budget, and a cap on how many Pods and other objects it can create. Define the rules in a YAML file — quota.yaml:

apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-team-quota
  namespace: dev
spec:
  hard:
    requests.cpu: "4"
    requests.memory: "8Gi"
    limits.cpu: "8"
    limits.memory: "16Gi"
    pods: "20"
    services: "5"
    persistentvolumeclaims: "10"
    configmaps: "20"
    secrets: "20"

Breakdown: metadata names the quota and pins it to the dev namespace; spec.hard lists the maximum permitted values. Here's what the team gets:

A quota is not a promise that the cluster has capacity — the nodes must still actually have the room.

5Apply the Quota

If the dev namespace doesn't exist yet, create it — then apply:

oc create namespace dev          # (kubectl works identically)
oc apply -f quota.yaml

That's it. Kubernetes now has a resource budget to enforce for the namespace.

6Check How Much of the Quota the Namespace Is Using

Creating the quota is only half the job — you also want to know whether the namespace is comfortably inside its budget or bumping against it.

oc describe resourcequota dev-team-quota -n dev
oc get resourcequota -n dev
oc get events -n dev --sort-by=.lastTimestamp

The describe output shows Used vs Hard per resource. If CPU requests show Used: 1500m against Hard: 4, the namespace has 1.5 CPUs of requests against a 4-CPU budget — 2.5 CPUs of headroom.

Practical tip: when a deployment suddenly stops creating pods, check quota usage first — the namespace may simply have hit its budget.

8What If the Pod Belongs to a Deployment?

This is where things get confusing. You apply a Deployment — Kubernetes accepts it — but the expected Pods never appear. Why?

A Deployment manages ReplicaSets, which create Pods. The Deployment object itself doesn't consume quota — only the Pods do. So the Deployment exists happily while its ReplicaSet keeps failing to create Pods underneath.

ResourceQuota doesn't decide which app is more important — it enforces the budget you configured.

9One Common Gotcha: Missing CPU or Memory Requests

If a quota tracks CPU or memory requests, a Pod that doesn't specify them can't be counted — so admission rejects it. Same for tracked limits with omitted limit values. This is why LimitRange and ResourceQuota are used together: LimitRange supplies defaults.

apiVersion: v1
kind: LimitRange
metadata:
  name: default-container-resources
  namespace: dev
spec:
  limits:
    - type: Container
      defaultRequest: { cpu: "100m", memory: "128Mi" }
      default:        { cpu: "500m", memory: "512Mi" }
oc apply -f limitrange.yaml
Defaults are applied at admission — they don't rewrite pods that already exist.

11OpenShift Extras — ClusterResourceQuota & Scopes

Vanilla ResourceQuota is per-namespace. OCP adds ClusterResourceQuota (CRQ): one shared pool across many projects selected by label — "team A gets 12 CPU across dev, test, qa."

Selection is by namespace label (spec.selector.labels) or the openshift.io/quota annotation. Usage syncs slowly by design — plan buffer.

13The Takeaway: Give Every Namespace a Budget

The problem was never simply "too many Pods" — it was the absence of a boundary on how much of the shared environment one namespace could consume. ResourceQuota introduces that boundary; LimitRange keeps individual workloads sane inside it. Start with a namespace you know well, set a realistic budget, observe, and adjust from real usage — not guesses.

Small controls like this make shared clusters much easier to manage. Deploy broken? Check the quota first: oc describe quota -n <ns> — the fix is often right-sizing requests, cleanup, or an approved quota raise.
