1What ResourceQuota Is — and Why It Exists

Documented · reference guide

A ResourceQuota is a namespace-scoped object that sets a hard ceiling on the resources a namespace may consume. On a shared cluster it is the bulkhead — one team can never consume so much CPU, memory, storage, or object count that it sinks the others. Enforcement happens at admission time, before the object is ever persisted.

2The Governance Stack — How the Pieces Fit

ResourceQuota never works alone — the complete model has four layers:

LayerScopePurpose
ClusterResourceQuotaMany namespaces (label selector)OCP-only. A team-level pool spanning dev/test/qa projects
ResourceQuotaOne namespaceHard ceiling on Σ requests, Σ limits, storage, object counts
LimitRangeOne namespacePer-container defaults/min/max — makes quota enforcement usable
requests/limitsEach containerThe units the quota counts
Critical interaction: once a compute quota (requests.cpu/requests.memory) exists, every new pod must declare those values or it is rejected. A LimitRange with defaults is what keeps developer pods from failing en-masse.

3Enforcement — Where the Rejection Happens

Quota is enforced by the API-server admission controller — not the scheduler or kubelet. status.used is a cache refreshed asynchronously (resource-quota-sync-period, default 5m).

sequenceDiagram participant U as User / CI / ArgoCD participant A as API Server admission participant Q as ResourceQuota plugin participant E as etcd U->>A: create Pod / PVC / Service A->>Q: check namespace quotas Q->>Q: used + requested ≤ hard? alt Within quota Q-->>A: ALLOW A->>E: persist object A-->>U: 201 Created else Exceeds quota Q-->>A: DENY A-->>U: 403 exceeded quota end
  • Failures surface as 403 Forbidden … exceeded quota — not as Pending pods.
  • Quota counts requests (and limits), never real usage.
  • status.used can lag real objects by up to the sync period.

5OpenShift-Specific Mechanics

ClusterResourceQuota — one pool, many projects

flowchart TB CRQ["ClusterResourceQuota: team-a-aggregate
hard: 12 CPU / 24Gi / 60 pods"] N1["project shop-dev · team=a"] N2["project shop-test · team=a"] N3["project shop-qa · team=a"] N4["project other · team=b"] N1 & N2 & N3 -->|share the single pool| CRQ N4 -.->|not selected| CRQ
  • Selected via namespace labels (spec.selector.labels) or the openshift.io/quota: <name> annotation.
  • CRQ usage syncs slowly by design (~minutes) — not for instantaneous enforcement.
  • A namespace can be selected by only one CRQ.
  • Never put user quotas on openshift-* / kube-* / default.
  • The Project Request Template can inject quota+limitrange into every new project — the clean way to make quotas default-on.

6Reference Manifests

Standard compute + object quota

apiVersion: v1
kind: ResourceQuota
metadata:
  name: app-quota
  namespace: <target-namespace>
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
    persistentvolumeclaims: "5"
    requests.storage: 50Gi
    services.loadbalancers: "0"
    services.nodeports: "0"

The LimitRange that makes quotas usable

apiVersion: v1
kind: LimitRange
metadata:
  name: app-limits
  namespace: <target-namespace>
spec:
  limits:
  - type: Container
    default:        { cpu: 500m, memory: 512Mi }   # injected when pod omits limits
    defaultRequest: { cpu: 100m, memory: 128Mi }   # injected when pod omits requests
    max:            { cpu: "2",  memory: 2Gi }
    min:            { cpu: 50m,  memory: 64Mi }
Without this LimitRange, every pod lacking requests fails admission the moment the compute quota exists.

Quick diagnosis commands

# which quotas exist + usage
oc get quota -n <target-namespace>
oc describe quota <quota-name> -n <target-namespace>

# pods with NO requests (rejected once compute quota exists)
oc get pods -n <target-namespace> -o json | \
  jq -r '.items[] | select([.spec.containers[].resources.requests.cpu] | any(. == null)) | .metadata.name'

# multi-project quota
oc describe clusterquota <crq-name>

9Best-Practice Checklist

  • ☐ Every user namespace gets both ResourceQuota and LimitRange (project template or GitOps)
  • ☐ scopes: [BestEffort] + pods: "0" — or LimitRange defaults — prevents unbounded pods
  • ☐ Object-count quotas (configmaps, secrets, services) — they protect etcd, not nodes
  • ☐ services.loadbalancers / nodeports pinned to 0 where not needed
  • ☐ ClusterResourceQuota for team pools; per-namespace ResourceQuota for hard walls
  • ☐ Alert on used / hard > 80% — run scripts/quota-audit.sh
  • ☐ Quota changes via PR with approval — quota is policy
